> 三款玩法，一个房间码，一副随时能开局的牌。
> 前端零构建，后端单进程，整套东西塞在 NAS 里，连上同一个 Wi-Fi 就能玩。
> 这是我从「想玩」写到「家里人真的在用」的一个项目。

- **我的角色**：规则设计、服务端、前端、部署，一个人
- **技术栈**：Node.js / Express / Socket.IO / node:sqlite / 原生 ES Modules + CSS / Docker
- **规模**：3 款已上线 + 1 款排期，2–10 人同房（超级梦幻可到 12 人）
- **运行方式**：Docker 部署在 NAS，容器内监听 9876，局域网访问

## 先有场景，再有代码

家里聚会，牌具总是凑不齐：麻将在老家，扑克少两张，骰子不知道滚哪去了。

买一副能解决一次，解决不了每次。所以我想要的东西很具体：**手机浏览器打开就能进房，不装 App，不注册也能玩**。

顺便，它得能一直跑在我那台 NAS 上——不占额外机器，不用管服务器。

## 三款玩法，一套房间

游戏规则各不相同，但房间、座位、准备、结算这些脏活没必要重写三遍。

- **推饼子**：40 张麻将牌（1–9 筒各 4 张 + 幺鸡 4 张），每人两张，点数相加取个位，0 点最小；对子大于任何点数。上下两叠牌墙，切牌只切上层。
- **纸牌西游记**：54 张经典版 / 36 张精简版两套规则，角色牌力 + 克制链，管不住就罚杯。
- **超级梦幻**：两张暗牌想象第三张，闲家押酒、庄家开牌，闷牌和锁酒把心理战拉满。
- **骰子吹牛**：排期开发中。

共用的是大厅、房间码、2–10 人座位、准备机制、机器人补位、逐局战绩、积分商城和个性化设置。

> 新玩法的接入成本，基本等于「写规则 + 注册一个模块」。

```js
// server/games/registry.js
registerGame({
  id, name, minPlayers, maxPlayers,
  configSchema, defaultConfig, normalizeConfig,
  rulesSummary,
  createState, applyAction,      // 服务端权威状态机
  waitingSeats, pendingBotActions,
  serialize,                     // 按视角下发给前端
});
```

房间创建弹窗里的配置项（人数、大小王、顺子与金花谁大、叫酒上限……）由 `configSchema` 自动生成，不用为每款游戏单独写表单。

## 技术选型：能少一层就少一层

单进程 Node，Express 负责静态文件与 HTTP，Socket.IO 负责实时同步，`node:sqlite` 存数据。

前端不用框架、不打包，原生 ES Modules + CSS3 直接上。原因不复杂：这东西跑在 NAS 上，构建链越短越不容易坏；出问题时 SSH 进去看日志就能定位，不用先怀疑构建产物。

代价是前端要自己管模块和渲染，但换来的是零构建、零运行时依赖，以及一个能在 ARM 小机器上跑得很稳的服务。

## 最难的不是规则，是牌墙

推饼子的规则本身不复杂，真正花时间的是**牌墙怎么切**。

真实牌桌上，牌是码成上下两排的。如果只在单叠牌墙上做循环移位，切牌本质上只是换了个起点，发出来的组合几乎没变——玩家会觉得「切了个寂寞」。

所以牌墙做成上下两叠：

- 洗好的 40 张按**奇偶交替**拆分，奇数位进上层，偶数位进下层，各 20 张
- 每家先抓上层一张、再抓下层一张
- **切牌只切上层**，下层一张不动

这样上层牌序被真正重排，每家「上层那张」全变，组合才会跟着变。切牌从此有了意义，而不是一个仪式感按钮。

前端用 3D 透视渲染两层牌墙和剩余张数，切牌动画只动上层——视觉和规则得对得上，否则玩家会怀疑你在糊弄。

## 手牌不能靠前端藏

多人游戏最怕的不是 bug，是**信息泄漏**：只要牌面下发到了客户端，抓包就能看见。

超级梦幻比牌时尤其敏感——如果所有闲家都能看到庄家的牌，后面的人照着决定「服不服」，庄家就没法玩了。

做法是服务端按视角脱敏：

- 比牌亮牌只对「被开的闲家 + 庄家」可见，其他人收到的是牌背
- 非当事人收到的数据里，牌面字段直接是 `null`，抓包也拿不到
- 本局结算只公开庄家与被开过牌的闲家；未被开牌的闲家保留手牌进下一局
- 所有动作在服务端二次校验：只有被罚的人能点「喝完了」，只有第一名能开下一局

这条原则很土，但很有效：**客户端负责好看，服务端负责正确**。

## 规则必须有测试

牌类游戏的 bug 特别隐蔽：某手牌型算错，可能几十局才碰上一次。

所以规则层是纯函数，配了三层测试：

- 每款游戏的规则单测（牌型、比牌、结算、边界）
- 百场窗口模拟，验证战绩裁剪和长期胜率不会算歪
- Socket 端到端联调，覆盖建房、准备、发牌、出牌、结算的完整链路

机器人也共用同一份「合法着法」计算结果——前端高亮能点的牌和引擎认可的牌来自同一个函数，不会出现「界面能点、服务端不认」。

## 部署在 NAS 上

`docker compose up -d --build`，容器内固定 9876，数据目录挂到 `./data`，镜像支持 x86_64 与 ARM64。

家里人用手机打开 `http://<NAS_IP>:9876` 就行，不用装任何东西。

后来加了「管理后台一键更新」：网页上点检查更新，自动拉镜像、重建容器，不用 SSH。代价是要把 `docker.sock` 挂进容器——这等于把宿主机的容器控制权交出去。家庭内网可以接受，如果这台 NAS 还跑着别的重要服务、或者对公网开放，就别这么干，老老实实 SSH 手动更新。

## 现在跑成什么样

- 三款玩法稳定可用，第四款在排期
- 账号、游客、战绩、积分商城、背包、主题与牌面皮肤都已接入
- 音效和背景音乐是 Web Audio 实时合成的，语音播报用 edge-tts 预合成，运行时不访问外网
- 掉线座位保留 45 秒，期间由托管代打，不会卡住整桌

## 还没做完

- 骰子吹牛还没开工
- 移动端横屏和折叠屏的适配只能算及格
- 战绩只保留最近 100 场，没有长期统计和赛季概念
- 目前只考虑局域网，没做公网部署和内网穿透方案
- 观战模式有，但没有回放分享

## 这个项目教会我的

规则可以慢慢调，**状态和权限必须先想清楚**。哪张牌谁能看、哪个动作谁有权发、结算以谁为准——这些定下来，后面的玩法都是在这套骨架上长出来的。

还有就是：能跑在 NAS 上、家里人愿意用，比任何技术指标都实在。
