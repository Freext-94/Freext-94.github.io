## 改一句话，凭什么要发一次版

先说以前的难处。

传统个人主页的套路：买服务器、装数据库、写后台、做登录。为了放五段经历、十个技能，先养一套系统。

难吗？不难。值吗？不值。

作品集一年更新三四次，维护成本却按天算。更别扭的是，改一句简介要开编辑器、找到那行字、改完提交、等部署。内容在云端，修改卡在代码里。

所以先把规矩立住：

- 改内容不碰代码，最好手机上就能改
- 不买服务器，不养数据库
- 半年后回来，它还得自己跑

规矩立住了，方案才有得选。

## 后台？Notion 就是

第一个决定：不写后台。

我建了五个数据库，字段直接对着页面上的位置摆：

- **Profile**：姓名、职业定位、简介、城市、学历、社交二维码，首页只读第一条
- **Projects**：项目名、摘要、分类、技术栈、封面、Slug、排序、精选
- **Skills**：技能、分类、技能定位、熟练度、标签、是否展示
- **Experience**：公司、职位、起止时间、职责、成果、排序
- **Articles**：标题、摘要、标签、封面、发布时间、状态，暂时空着

几个当时想清楚、后来救命的细节：

- **封面存 URL，不存文件**。Notion 托管的文件，API 给的是带签名的临时链接，一小时就过期。构建一次网站，图片全变红叉——这事我踩过，不烧心才怪。
- **熟练度用百分比数字**，`0.85` 和 `85` 都认，手滑填错也撑不爆进度条。
- **「是否展示」是开关**，不想露的技能取消勾选，不用删数据。
- **排序是数字**，越小越靠前；经历按 5、6、7、8 排，数字小的就是最近那段。

> 我原以为要写个后台。结果后台是现成的，我要写的只是个翻译——把 Notion 的字段翻成页面。

## Astro 只管一件事

第二个决定：不做 SSR，全部静态生成。

访客打开页面时，没有数据库查询，没有 API 调用，没有冷启动。构建时把 Notion 读完，生成一堆 HTML，之后谁来都一样快。Notion 当天挂了，网站照开。

数据流就三层：

{{embed:https://freext-94.github.io/projects/personal-portfolio/architecture.html}}

- **notion.ts** 取数。填数据源 ID 或直接粘数据库链接都能认；网络抖了就重试五次，间隔一次比一次长。
- **normalize.ts** 翻译。富文本拼成句子，职责按「一行一条」或「整段句号」拆成要点，`中国大陆成都` 洗成 `成都`。
- **pages/** 排版。首页、作品集、`[slug]` 详情，路由构建时就定死。

## 让流水线自己上班

第三个决定：内容更新不占周末。

整条流水线一句话：推到 main，剩下的交给 GitHub Actions。

```yaml
on:
  push: { branches: [main] }
  schedule: [{ cron: '0 18 * * *' }]  # 北京时间每天 02:00
  workflow_dispatch:

jobs:
  build:
    steps:
      - 检查 Notion 配置   # 缺 Secret 直接失败，不静默
      - npm ci
      - npx astro check    # 类型与组件检查
      - npx astro build    # 构建时读取 Notion
      - 上传 dist 产物
  deploy:
    needs: build
    steps: [deploy-pages]
```

两个刻意设计：

- **配置检查单独成步**。以前 Secret 漏配，构建会拿示例数据悄悄通过——等于把一份假简历发上线。现在缺配置直接红，日志里写明缺哪一项。
- **每天定时跑一次**。Notion 改了不会通知网站，定时任务是兜底；想立刻生效，手动触发一次。

## 翻车五次，才算入门

流程跑通那天，我以为稳了。结果真正的坑才开始。

**第一坑：Notion 改版，数据库 ID 不好使了。**
API 升到 2025-09-03，查询只认 `data_source_id`，拿数据库 ID 去查，直接报找不到。解法是先按数据源查，明确报 `object_not_found` 才降级去解析数据库。注意，网络错误不能当成「找不到」，否则一次超时就被判成 ID 错了。

**第二坑：环境变量集体失踪。**
Vite 在构建期做静态替换，`import.meta.env[key]` 这种动态写法，开发环境好好的，一构建全是 `undefined`。它还不报错，页面突然就空了。只能老老实实把五个变量逐个写成字面量。

**第三坑：本机 DNS 坑我半小时。**
域名解析出一个能用的 IPv6 和一个不可达的 IPv4，请求经常卡在连接超时。改成 IPv4 优先，构建成功率才稳住。这跟代码没关系，可它能让 CI 随机失败。

**第四坑：示例数据差点上了生产。**
本地没配凭证时会退回示例数据，方便调样式。生产构建也这么干，就等于把模板内容发布了。现在生产缺配置直接抛错——宁可构建失败，也不让假数据上线。

**第五坑：Notion 的文字不能直接塞进 HTML。**
详情页正文走 `set:html`，富文本里要是出现 `</script>`，页面当场被截断。解法是先全部转义，再按白名单包标签，链接只放行 `http`、`https`、`mailto`。

> 难的不是把页面做出来。难的是半年后它还能自己跑，出错时还错得明显。

## 算笔账

- **服务器**：0 元。静态站不需要
- **数据库**：0 元。Notion 免费版够用
- **域名**：0 元。用 `github.io` 子域
- **CI/CD**：0 元。公开仓库的 Actions 额度足够
- **图床**：复用已有服务，没为这个项目单独花钱
- **上线延迟**：手动触发一两分钟；忘了触发，最晚第二天凌晨

代价也说清楚：

- 内容不是实时生效，改完要等一次构建
- 搜索、评论、点赞这类要服务端的功能，做不了
- 文章库还空着，首页连「文章」区块都不显示

这套方案谈不上多高级，胜在不烧心：不用半夜起来看服务器，也不用担心账单。

## 还没做完的

不打算把它写成「完美案例」，缺口明摆着：

- 文章详情页没做。Articles 的 `Slug` 字段留着，等有内容再补
- 没有 404 页面，访问错链接看到的是 GitHub 默认页
- 没有 sitemap 和 robots.txt，收录全靠缘分
- 没有访问统计，至今不知道有没有人来过
- 构建失败没通知，只有我主动看 Actions 才知道
- 分享链接没有预览图，`og:image` 一直空着
- 图片还是手贴 URL，没有上传流程
- 没有搜索和标签筛选，项目多了会难找
